## 2. PR #29 / PR #31 的历史根因

PR #29（merge commit `ec1cd4381bddc8ed77603d4a80b7b150bb4733eb`）名义上同步 v0.1.176，但其分支不是从精确的官方 v0.1.176 tree 重新构造。历史关系验证显示：

- PR #21 的 workbench/test console merge `bd2428092` 是 PR #29 的祖先；
- 回退 PR #21 的提交 `203bb5069` 不是 PR #29 的祖先；
- 因此 PR #29 的同步链重新携带了已经在另一条线上撤回的开发/测试控制台 UI；
- PR #29 合并本身包含 `722 files changed, 62772 insertions(+), 4776 deletions(-)`，除上游更新外还叠加了大范围 UI 和 feature overlay，无法把它视为官方 v0.1.176 的可审计重放。

PR #31（merge commit `8e3821377be8c04e377731aa6c7c42d1bb1c2273`）通过 `de1ec7567` 回退 PR #29，并选择性恢复当时批准的首页、注册/认证安全和 CodeQL 内容。这个处理正确地阻止了 PR #29 overlay 继续留在 `aiwelink-dev`，但它回到了较旧应用基线，仍没有形成“官方 v0.1.176 tree + AIWeLink 最小差异”的发布候选。

根因不是单个冲突文件选错，而是同步策略错误：历史分支把开发/test console UI 和大 overlay 当作同步输入，随后再通过 merge/revert 纠正；它没有从官方发布 tree 出发建立可复核的差异边界。

## 3. 本次重建方法

本次采用确定性重建，而不是整体合并历史分支或无差别 cherry-pick：

1. 以 `origin/aiwelink-dev` 的 `6ac698e7d` 保持 PR 合并连续性；
2. 验证 `v0.1.176` peeled 到 `e803e3851c0a7e222cfadeafad7b8636ab959d11`；
3. 用提交 `4be884fc1` 恢复精确的官方 v0.1.176 应用 tree；
4. 只重放预先列入 allowlist 的 AIWeLink 行为，每个冲突以官方 v0.1.176 实现为主体，仅加入必要的 AIWeLink hunk；
5. 用同步和 CI contract 固化版本、官方 UI 和禁止项；
6. 最后直接比较 `HEAD` 与官方 peeled commit，按路径和内容审计，而不是根据提交标题推断结果。

这种方法保留了 `origin/aiwelink-dev` 的历史可合并性，同时把应用内容来源收敛为一个精确 tag 和一份显式 allowlist。后续审计可以回答每个非官方差异为什么存在。

## 6. Release 不可变性

发布链新增或确认了以下约束：

1. `.github/workflows/release.yml` 只监听严格的版本化 tag glob `v*.*.*-*`；
2. `backend/scripts/validate-version.sh` 进一步要求输入必须精确等于 `v$VERSION`，因此本版本只能使用 `v0.1.176-1`，`0.1.176-1`、`refs/tags/v0.1.176-1`、`v0.1.176` 和 `v0.1.176-2` 均被拒绝；
3. validate job 解析并输出已验证的 `release_sha`，frontend build 和 release job 都按该 SHA checkout，不再在后续 job 中按可移动 tag checkout；
4. 首次校验 tag peeled SHA 必须等于 `release_sha`；
5. release job 执行 `git fetch --tags --force` 获取完整/可能更新的 annotated tag 后，再次解析 tag peeled SHA 并与原 `release_sha` 比较；如果 tag 已移动则中止；
6. `.goreleaser.yaml` 和 `.goreleaser.simple.yaml` 都不向该仓库 GHCR 发布 `latest`。full 配置的 GHCR 使用 version、major/minor 和 major tag，simple 配置只使用 version/architecture tag；两种配置均没有 GHCR `latest`。

这里区分 release 镜像与日常分支镜像：`backend-ci.yml` 可在 AIWeLink 私有 registry 为 `main` 发布日常 `latest`，但 versioned release 不会把 `latest` 发布到该仓库的 GHCR，且私有 release 镜像也只使用明确版本号。

## 9. 风险和后续维护边界

- `origin/aiwelink-dev` 历史中仍包含 PR #29 merge 和 PR #31 revert；这不影响本次最终 tree，但意味着未来不能用“祖先中已有 v0.1.176”判断同步是否完成；
- 未来同步必须比较官方 tag tree 与最终 tree，不能简单回退 PR #31、重放 PR #29 或整体合并旧 sync 分支；
- allowlist 中的认证和版本 UI 差异可能与后续官方实现重叠；发生冲突时优先采用新官方实现，只移植仍然必要的 AIWeLink 行为；
- channel-monitor-v2 属于当前官方基线。后续如需改动，应作为独立、明确审批的功能变更，不能与“移除 PR #29 overlay”混为一谈。

## 10. 后续上游同步检查清单

1. **获取并验证 tag**：从官方 remote fetch 指定 tag，记录 tag object 和 peeled commit，验证它属于预期官方历史；不要信任同名残留本地 tag。
2. **刷新生产开发线**：fetch `origin`，记录最新 `origin/aiwelink-dev` SHA，并从它创建 `sync/upstream-v<version>-official-ui`；本地 `main` 只供历史参考。
3. **从官方 tree 重建**：把应用 tree 恢复到精确 peeled commit；不要通过 wholesale merge、回退的反向回退或大范围 cherry-pick 推导新基线。
4. **重放显式 allowlist**：预先列出注册、OAuth、版本、CI/release、部署、README/品牌和必要安全修复；逐 hunk 解决冲突，官方新实现优先。
5. **更新版本**：同步设置 `UPSTREAM_VERSION`、AIWeLink `VERSION`、strict release tag 和镜像 version；验证 tag 必须精确等于 `v$VERSION`。
6. **审计官方 UI**：比较 AppLayout、AppHeader、AppSidebar、两个 dashboard、`style.css` 和 `styles/`；搜索 workbench marker/tests；检查 Grok/pricing/billing/audio/web-search/model-mapping 等禁止 overlay 路径；单独确认官方自带功能（例如 channel-monitor-v2）是零差异保留还是经明确批准修改。
7. **执行聚焦验证**：运行 upstream/CI contract、受影响 Go packages、前端聚焦测试、pnpm frozen install、typecheck/build、README link、secret/default scan 和 `git diff --check`；记录工具不可用或环境限制，不把未执行项写成通过。
8. **两阶段审查**：先做 spec/allowlist 审查，确认需求和排除项；再做 code-quality/diff 审查，确认实现、测试、release 不可变性和最终官方 UI diff。
9. **创建 ready PR**：目标固定为 `aiwelink-dev`，PR 说明列出 source tag/SHA、base SHA、allowlist、排除项、验证和回滚；创建 ready PR，但不指定 reviewers，也不请求个人审核或 approval。

## 11. 回滚建议

不要整体回退“恢复官方 v0.1.176 tree”的提交来撤销某个 AIWeLink 定制，否则会重新暴露历史 overlay 或回到旧应用基线。需要回滚时按 allowlist 类别建立小范围 revert/fix PR：注册投递、OAuth 安全、双版本标识、release contract、CI/image publication 或 README 品牌分别处理，并重新执行相应聚焦测试和官方 UI diff audit。
